What a check cannot see

A check is only as true as the design file

  • A file that says "ksa_cloud" for a service deployed abroad passes.
  • An evaluation set in the wrong language passes check 1.
  • A design that meets every rule may still miss its scenarios.

So

Checks catch what can be read from the file on every commit; a review asks whether the file and the design are right, once per design.

Infrastructure as code

Revert a hand change nobody approved; codify one that was

Changed by hand in a console

One person decides and applies; no record of why; the fitness checks never see it; rebuilding in another region depends on memory.

Declared under version control

A second person reviews each change; checks run before it applies; a revert is one commit; the same files rebuild the platform.

For the three drifts. Apply the declared file again for the fallback and the retention, now. Write the reports budget into the code through a reviewed change, then apply.

Emergencies happen: the rule is not "never touch the console" but "an emergency hand change carries a ticket and is codified or reverted within one working day". A change without a ticket is reverted, even when it looks harmless.

A parallel case for practice: the waste team's nightly batch is declared with 8 parallel calls and runs with 20, changed by hand with no ticket. Its data is Public, so no placement rule breaks; it is still reverted, and the team asks for 20 through a reviewed change if it needs them.
