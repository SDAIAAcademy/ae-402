Choosing by questions, not habit

Five questions choose the pattern before anyone names a model

  1. What is the output? A label, a cited answer, a document, an action.
  2. Are there labelled examples? Thousands change the options.
  3. Who is waiting? A person in seconds, a process in minutes, nobody until morning.
  4. How many steps, and does each depend on the last?
  5. How does the data change? Stable, weekly, live.

The columns of needs.csv are the answers to these five questions. Ask a table to answer them for one of their own systems before the lab.

A common confusion

Retrieval brings knowledge; fine-tuning shapes form

Retrieval

The building code changes with each circular. Retrieval reads today's version and cites it. Updating means re-indexing, not retraining.

Fine-tuning

Inspection letters follow one house style. 9,000 approved letters can teach the form; facts still come from the inspector's notes.

What goes wrong. Tuning a model on the code to "know" it: the next circular makes the model wrong and nobody can see where.

For N6 the lab's answer is fine-tuning, but a prompt with three examples is a fair rival: the match is a hypothesis to test, as step 3 tests N2. Fine-tuning itself is taught in AE-310; here it is an option with a cost and an exit.

Agentic

Choose an agent only when the next step depends on the last result

taskpre-check submission 2027-114 for missing documents
step 1read the forms: building type is a commercial extension
step 2so query the permits system for the fire-safety approval
resultapproval missing
outputtwo documents missing, with the clauses that require them

Step 2 exists only because of step 1's result. A status question has one step and needs no agent: an agent there adds cost, latency and a larger attack surface for nothing. Agent engineering is AE-302's subject; the architect's decision is whether to use one.

When nobody is waiting

Batch and event-driven designs move work off the user's path

Batch

Thirty district summaries a night: run them together at off-peak capacity, retry failures, and nobody sees a latency.

Event-driven

A status change publishes an event; a notifier reacts. 40,000 notices a month, and no applicant has to ask.

Every status notice that is sent is a status call that is not made: the driver S02 is served by an event, not by a chat.

This is the integration topic: Muyassir talks to the permits system through a read API, and the notices through events. Ask: which of the two would you put on the Asas platform as a shared capability? Day 3's demand matrix answers it with data.

The non-generative baseline

Cost one option without a generative model, every time

  • It shows what the generative model must beat, in quality and in cost.
  • It is the fallback when the model is down or over budget.
  • Sometimes it wins outright, as for report routing.
  • When it loses, say on what: for Muyassir, it answers 70% of questions against 92%.

LO3 asks for at least three options including a non-generative baseline. Session 2 costs O3 for Muyassir; it loses there, on coverage, which is an honest and useful finding for the options paper.

Weighted criteria

Weights are opinions; report how far they can move

  • Double counting. Three-year cost and exit cost are both money; say so, or merge them.
  • Ordinal scores. A 4 is not twice a 2; small score gaps are noise.
  • Hidden weights. A criterion left out has weight zero, by decision.
  • Rank reversal. Find the weight at which the leader changes, and print it.

The entry names "weighted criteria and their pitfalls". The fix is not to drop weights; it is to show the sensitivity of the ranking to them, exactly as Session 2 showed the sensitivity of cost to volume.

Buying the exit down

A procurement requirement keeps the exit open only if it can be verified

WeakThe provider will make data available where possible.
VerifiableThe provider shall export all indexed documents, their embeddings and metadata in JSON Lines or Parquet within 10 working days of a request, at no extra charge.

The lab's lint checks three things: "shall", something verifiable (a number, a format, a standard interface) and no escape phrase. Content is the participant's: each requirement must remove one of O1's factors. The second solution requirement asks for an OpenAI-compatible interface and a 90-day notice after 12 months.

Checkpoint

Which requirement removes O1's largest exit cost?

O1's largest exit factor is its managed vector store with no bulk export (SAR 250,000). Which requirement removes it?

The service shall expose an OpenAI-compatible interface
The provider shall export the index, embeddings and metadata in JSON Lines within 10 working days
The contract shall allow exit with 90 days' notice
The provider shall give reasonable help on exit
Why. The cost is in the data; only an export of the data, in an open format and a set time, removes it.

Answer: B. A and C are both good requirements for other factors; that is the trap.

The flip search must rescale the other weights; participants who only add weight to exit cost get weights that sum above 1 and a flip that means nothing. The lint is strict on "shall": "will" fails on purpose.

The decision log

Six records make a log when they share an index and a status

  • One file per decision, numbered, never renumbered.
  • Status: proposed, accepted, or superseded by a later number.
  • An index with each record's trigger, so triggers are watched in one place.
  • Records are reviewed in pull requests like code.

The stretch of Lab 2.4 writes the index. A superseded record is never deleted: the history of why is the point.
